Triangulate

The jury that leaves a signed receipt. Give the same coding task to Claude, Codex, Gemini, and Grok at once, then diff what they produced, arbitrate deterministically, and merge the best output — with a signed, content-addressed verdict that records every disagreement.

Repository on GitHub · Apache-2.0 · TypeScript / Node 24+ · single-package CLI

Demo video

1. The run

One task, four jurors, each in its own git worktree off HEAD. The command as typed:

$ tri run --task "add a subtract function next to add" --repo ./demo --models claude,codex,gemini,grok --fake --out verdict.json

What makes it different

  • Signed, content-addressed verdicts. Every verdict is an Ed25519 JWS over a canonically-serialized payload; its id is the SHA-256 of that payload. tri verify recomputes both offline. A tampered verdict fails; a verdict with fields deleted fails too.
  • Deterministic merge, not an LLM's opinion. Line-level 3-way merge with AST-aware refinement, then the repo's own tests settle what the rules can't. Conflicts are recorded with both sides — never silently resolved.
  • The verdict is the product. triangulate/1 is a versioned, machine-readable format other tools can consume; the first consumer is Vouchard scorecards, which can cite a verdict id.
  • Cost is a feature, never a claim. Per-juror cost is reported only when the tool reports it, never invented; per-juror and global budgets are enforced.

Honest limits — stated, not hidden

  • This demo used --fake scripted jurors. No live model was called and no real-model run has been demonstrated from this environment (no model credentials here). A live run needs the model CLIs and keys on a machine that has them; the Claude/Gemini invocations are best-effort against their documented flags, Codex's flags were verified against the installed binary.
  • A verdict is a record, not a proof of correctness. Agreement is evidence, not truth. Models that share training data are not independent jurors.
  • Test-pick runs candidate code unsandboxed, as you. The test environment is scrubbed (PATH and locale basics only, HOME and TMPDIR pointed at scratch directories, test command pinned to the base repo's definition) — but a determined same-user process can resolve your real home from the passwd database on any OS and read a parent's environment via /proc on Linux. The signing key is the one exception: key.pem is passphrase-encrypted at rest (scrypt + AES-256-GCM), so a stolen copy is ciphertext. Everything else under your home is reachable by candidate code. If that is not acceptable for a task or a repo, use --no-test.
  • Model CLIs run unsandboxed too. A prompt-injected CLI runs with your real HOME (it needs its own auth config there) and could read your files — including the signing key file, which is ciphertext without the passphrase.
  • No revocation in v1. If your key is lost or replaced, verdicts signed by the old key can no longer be re-signed, and a new key starts a new identity.
  • Cost budgets are enforced at completion for CLI adapters (they cannot observe cost mid-run); only the fake adapter enforces mid-run. The run itself is bounded by timeout.

Run it yourself

npm install -g @tamtunnel/triangulate
# or: npx @tamtunnel/triangulate

# One task, four jurors, in a git repository:
tri run --task "Add a subtract function next to add" --repo ./my-project

# See what happened:
tri show triangulate-verdict.json
tri diff triangulate-verdict.json

# Verify the verdict offline (no network, no registry):
tri verify triangulate-verdict.json

# No credentials? Try the pipeline for $0:
tri run --task "Add a note" --repo ./my-project --fake --no-test

Requirements: Node 24+, a git repository (the base is HEAD), and the model CLIs you want to use — Claude Code (claude), the OpenAI Codex CLI (codex), the Gemini CLI (gemini) — plus XAI_API_KEY for Grok, which ships as an API adapter (there is no mature Grok coding CLI). Each juror gets only its own key; keys never appear in a verdict, a log, or an error message.
